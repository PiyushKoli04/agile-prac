Start here: rules that prevent most problems

Docker Desktop must be open and runningPracticals 6, 7, 8, 9 and 12 all need it. Open Docker Desktop first and wait for the green “Engine running” label. Then run docker version. You must see both a Client and a Server section. If Server is missing, the engine is not running yet.
  • One folder per practical. Create it in VS Code (File → Open Folder, or the New Folder icon), then open the terminal with Ctrl + `. Always check the terminal path shows the right folder before running commands.
  • Save every file with Ctrl+S before running a command. Unsaved files are the most common reason a result looks wrong.
  • Run commands one at a time and read the output. Do not paste a whole block blindly.
  • File names matter. Dockerfile has no extension. In VS Code, check that Windows did not save it as Dockerfile.txt.
  • YAML files (.yml) use spaces, never tabs. Indentation errors are the main YAML failure.
  • Ports can clash. Each practical below uses a different port so you can keep things running: Jenkins 8080, Docker page 8081, Compose 8082, Prometheus 9090, Grafana 3000.
  • Take screenshots as you go. Each practical lists what to capture. Include the terminal command and its output.
  • Clean up containers with the commands at the end of each practical, so the next one starts clean.

1.Create a Jira task

Project StudentProject with one task, Complete Project Documentation, assigned to you.

Theory: what we did and achieved

Concept: Jira is a project management tool used by teams to plan and track work. A project groups related work, and each piece of work is an issue such as a task, bug or story. Assigning an issue to a person makes them responsible for it.

What we did: We created a Kanban project named StudentProject, created a task called Complete Project Documentation, and assigned it to ourselves.

What we achieved: We learned the basic Jira structure (site, project, issue) and how work is created and owned. This is the first step of the DevOps planning stage, where work is defined before anyone builds it.

  1. Go to atlassian.com/software/jira and click Get it free. Sign up and choose a site name, for example yourname-devops.
  2. Click Projects → Create project. Pick the Kanban template and Team-managed.
  3. Set Name to StudentProject and click Create.
  4. Click the blue Create button in the top bar. Set Project = StudentProject, Work type = Task, Summary = Complete Project Documentation.
  5. In Assignee choose Assign to me. Click Create.
  6. Open the card on the board and confirm your name shows as Assignee.
Screenshots: the board with the project name; the open task showing title, assignee and status To Do.
RememberThe task is created inside the project, so check the Project field shows StudentProject, not another project.

2.Track task progress in Jira

Task Testing Activity moved To Do → In Progress → Done.

Theory: what we did and achieved

Concept: Every Jira issue has a status that follows a workflow. A Kanban board shows this workflow as columns, usually To Do, In Progress and Done, so everyone sees the state of the work at a glance. Jira also records every change in the issue history.

What we did: We created a task named Testing Activity and moved it from To Do to In Progress, then to Done, and viewed it afterwards.

What we achieved: We tracked a task through its full life cycle and saw the history as proof. This shows how teams monitor progress and keep work visible and accountable.

  1. Open StudentProject. Click Create, Work type = Task, Summary = Testing Activity, then Create.
  2. Screenshot the card in To Do.
  3. Drag the card to In Progress (or open it and use the status dropdown). Screenshot.
  4. Drag it to Done. Screenshot.
  5. Display it: open the card and scroll to Activity → History. It lists To Do → In Progress → Done.
Screenshots: three board states, plus the history view as proof of both transitions.
RememberTake the screenshot after every move. You cannot recreate the In Progress state later without moving the task again. If the card vanishes from a Kanban board after Done, find it with Filters → View all work items.

3.Git branch and merge

Repository, branch feature, student.txt committed, merged into main.

Theory: what we did and achieved

Concept: Git is a version control system that records the history of a project. A repository stores that history. A branch is an independent line of development, so new work can be done without touching the stable main branch. Merging combines the finished work back into main.

What we did: We created a repository, made a first commit, created a branch named feature, added and committed student.txt there, then switched to main and merged feature into it.

What we achieved: We learned the core Git workflow of init, add, commit, branch and merge. Branching lets teams work in parallel safely, which is the basis of source code management in DevOps.

  1. In VS Code create a folder git-practical and open it. Open the terminal.
  2. Create readme.txt in VS Code with any text and save it.
git init -b main
git add readme.txt
git commit -m "Initial commit"
git checkout -b feature
git branch
  1. In VS Code create student.txt containing your name and save it.
git add student.txt
git commit -m "Add student.txt"
git checkout main
git merge feature
git log --oneline
git branch
Screenshots: git branch showing both branches; the merge output; git log --oneline; student.txt visible in the VS Code explorer while on main.
RememberCommit readme.txt first, since a branch needs one commit to start from. Create student.txt after switching to feature, so the file belongs to that branch. If your branch is named master, run git branch -M main.
Troubleshooting: “Please tell me who you are”Run the one-time Git setup from the Start here section.

4.Resolve a Git merge conflict

Change the same line in two branches, merge, and fix the conflict.

Theory: what we did and achieved

Concept: A merge conflict happens when two branches change the same line of the same file differently. Git cannot decide which version is correct, so it stops and marks the file with conflict markers. A person must choose the final content.

What we did: We changed line 1 of one file on both main and feature, committed both, merged, saw the conflict, edited the file to remove the markers, and committed the result.

What we achieved: We created and resolved a conflict by hand. Conflicts are normal in team projects, so knowing how to read the markers and finish the merge is an essential Git skill.

  1. Create a new folder conflict-practical in VS Code and open it. Create file.txt with one line: Hello from main. Save.
git init -b main
git add file.txt
git commit -m "Initial commit"
git checkout -b feature
  1. In VS Code change line 1 to Hello from feature branch. Save.
git add file.txt
git commit -m "Change line in feature"
git checkout main
  1. Now on main, change line 1 to Hello from main updated. Save.
git add file.txt
git commit -m "Change line in main"
git merge feature

Git prints CONFLICT (content): Merge conflict in file.txt. This is expected. Screenshot it.

  1. Open file.txt in VS Code. It shows markers: <<<<<<< HEAD, =======, >>>>>>> feature. Screenshot this.
  2. Edit the file so only the final line you want remains, for example Hello from main and feature combined. Delete all three marker lines. Save.
git add file.txt
git commit -m "Resolve merge conflict"
git status
git log --oneline --graph
RememberBoth branches must change the same line and both changes must be committed, otherwise no conflict appears. Save the file in VS Code after every edit. Never leave marker lines in the file.
Troubleshooting: stuck in the middle of a mergeRun git merge --abort to go back to before the merge and try again.

5.Create a GitHub repository

Repository DevOpsPractical with README, plus a feature branch pushed to GitHub.

Theory: what we did and achieved

Concept: GitHub is a web service that hosts Git repositories. The copy on your computer is the local repository, and the copy on GitHub is the remote, usually named origin. Pushing sends local commits to the remote, which allows backup, sharing and collaboration.

What we did: We created the DevOpsPractical repository on GitHub, created a local repository with a README, connected the two with a remote, pushed main, then created a feature branch and pushed it too.

What we achieved: Our code is now stored online and shared through a remote. This is the step that connects local work to the team and to later automation such as CI/CD pipelines.

  1. Sign in at github.com. Click + → New repository. Name = DevOpsPractical, choose Public. Leave “Add a README” unticked. Click Create repository.
  2. In VS Code create a folder DevOpsPractical and open it. Create README.md containing # DevOpsPractical and a line of text. Save.
git init -b main
git add README.md
git commit -m "Add README"
git remote add origin https://github.com/YOUR-USERNAME/DevOpsPractical.git
git push -u origin main
  1. Create the feature branch. Make a new file student.txt in VS Code and save it.
git checkout -b feature
git add student.txt
git commit -m "Add student.txt on feature branch"
git push -u origin feature
git branch -a
git remote -v
  1. Refresh the GitHub page. Open the branch dropdown and confirm main and feature both exist.
RememberReplace YOUR-USERNAME with your real GitHub username. Commit before the first push, or Git says the branch does not exist. The repository on GitHub must be empty, or the first push is rejected.
Troubleshooting: Authentication failedGitHub no longer accepts your account password in the terminal. Sign in through the browser popup, or create a Personal Access Token: GitHub → Settings → Developer settings → Personal access tokens (classic) → tick repo, and use it as the password.
Troubleshooting: “remote origin already exists”Run git remote remove origin and add it again.

6.Execute a Jenkins pipeline

Console output prints Welcome to DevOps Practical and Build Successful.

Theory: what we did and achieved

Concept: Jenkins is an automation server used for continuous integration and continuous delivery (CI/CD). A pipeline is a list of stages, such as build, test and deploy, written as code in a Jenkinsfile style script. Each stage runs automatically and its output appears in the console log.

What we did: We ran Jenkins in a Docker container, created a pipeline job, wrote a script with two stages that print messages, ran the build and read the console output.

What we achieved: We ran our first automated pipeline and saw it finish with SUCCESS. The same structure is later used to build, test and deploy real applications automatically.

Before you startOpen Docker Desktop and wait for “Engine running”. Confirm with docker version that a Server section appears. The error failed to connect to the docker API ... dockerDesktopLinuxEngine means Docker Desktop is not running.
  1. Start Jenkins (the first run downloads the image, so it takes a few minutes):
docker run -d --name jenkins -p 8080:8080 -p 50000:50000 -v jenkins_home:/var/jenkins_home jenkins/jenkins:lts
  1. Wait 1 to 2 minutes. Open http://localhost:8080.
  2. Get the unlock password and paste it in the browser:
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword
  1. Choose Install suggested plugins, wait, create your admin user, then Start using Jenkins.
  2. Click New Item, name it DevOpsPipeline, choose Pipeline, click OK.
  3. Scroll to Pipeline, keep “Pipeline script”, and paste:
pipeline {
    agent any
    stages {
        stage('Welcome') {
            steps {
                echo 'Welcome to DevOps Practical'
            }
        }
        stage('Build') {
            steps {
                echo 'Build Successful'
            }
        }
    }
}
  1. Click Save, then Build Now. Click build #1, then Console Output.
Screenshots: the pipeline script; the green build #1; Console Output showing both messages and Finished: SUCCESS.
RememberJenkins needs a minute after starting, so a blank page just means wait and refresh. Write down your Jenkins username and password. If the container stops later, restart it with docker start jenkins (your pipeline is kept in the volume).
Troubleshooting: container name already in use, or port 8080 busyName in use: run docker rm -f jenkins and run the start command again.
Port 8080 busy: use -p 9090:8080 and open localhost:9090.
Alternative if Docker will not workInstall Java 17 or 21, download jenkins.war from jenkins.io, then run java -jar jenkins.war --httpPort=8080. The password is printed in the terminal.

7.Build a Docker image

A simple page showing Welcome to Docker, built into an image and run in a container.

Theory: what we did and achieved

Concept: Docker packages an application and everything it needs into an image. A Dockerfile is the recipe for building that image. A container is a running instance of an image, isolated from the rest of the computer. Port mapping connects a port on your computer to a port in the container.

What we did: We wrote an HTML page and a Dockerfile based on nginx, built an image with docker build, ran it with docker run and opened it in the browser.

What we achieved: We turned a web page into a portable image that runs the same way on any machine with Docker. This solves the problem of an application working on one computer but not another.

Docker Desktop must be runningCheck with docker version before you start.
  1. In VS Code create a folder docker-practical and open it.
  2. Create index.html:
<!DOCTYPE html>
<html>
<head><title>Docker</title></head>
<body><h1>Welcome to Docker</h1></body>
</html>
  1. Create a file named exactly Dockerfile (no extension):
FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html
  1. Build, run and verify. The dot at the end of the build command is required.
docker build -t welcome-docker .
docker images
docker run -d --name welcome-container -p 8081:80 welcome-docker
docker ps
  1. Open http://localhost:8081. You should see “Welcome to Docker”.

Clean up afterwards:

docker rm -f welcome-container
Screenshots: the build output; docker images; docker ps; the browser showing Welcome to Docker.
RememberRun the commands from inside the folder that contains the Dockerfile. In -p 8081:80 the left number is your computer, the right number is the container. Use 8081, not 8080, because Jenkins may be using 8080.
Troubleshooting: “failed to read dockerfile”The file is probably named Dockerfile.txt, or you are in the wrong folder.

8.Run a Docker Compose application

Nginx web server started with Compose, with the page confirmed reachable.

Theory: what we did and achieved

Concept: Docker Compose describes one or more containers in a single YAML file, so the whole application starts with one command instead of long docker run commands. The file defines services, images, ports and volumes.

What we did: We wrote a docker-compose.yml that runs the nginx image, maps a port, and mounts our HTML folder into the container. We started it with docker compose up -d and checked the page with the browser and curl.

What we achieved: We ran a web server from a configuration file and verified it responds. This makes setups repeatable and easy to share, and it scales to applications with many containers.

Docker Desktop must be running. Compose is included with it, so there is nothing else to install.
  1. Create a folder compose-practical and open it in VS Code.
  2. Create a subfolder html, and inside it a file index.html with <h1>Hello from Docker Compose</h1>.
  3. Create docker-compose.yml in the main folder (indent with spaces):
services:
  web:
    image: nginx:alpine
    ports:
      - "8082:80"
    volumes:
      - ./html:/usr/share/nginx/html:ro
  1. Start and verify:
docker compose up -d
docker compose ps
curl.exe -I http://localhost:8082

The curl output should include HTTP/1.1 200 OK. Also open http://localhost:8082 in your browser.

Stop it afterwards:

docker compose down
Screenshots: docker compose up -d; docker compose ps showing the service Up; the browser page.
RememberIn PowerShell write curl.exe, not curl, because plain curl is a different command there. Run docker compose commands in the folder that holds the compose file. The newer command is docker compose with a space, not docker-compose.

9.Deploy an application in Kubernetes

Nginx deployment with three replicas, all three pods Running.

Theory: what we did and achieved

Concept: Kubernetes is a platform that runs and manages containers across a cluster. A pod is the smallest unit and holds one or more containers. A Deployment keeps a chosen number of identical pods (replicas) running and replaces any that fail. kubectl is the command line tool used to control it.

What we did: We enabled Kubernetes, wrote a Deployment YAML for nginx with three replicas, applied it with kubectl apply and checked the pods with kubectl get pods.

What we achieved: We deployed an application with three running copies. This shows how Kubernetes provides availability and scaling, which are the main reasons it is used for production systems.

Docker Desktop must be runningKubernetes here is the one built into Docker Desktop.

Turn on Kubernetes

  1. Docker Desktop → Settings (gear) → Kubernetes → tick Enable Kubernetes → Apply & restart.
  2. Wait until the bottom of Docker Desktop shows Kubernetes running (several minutes the first time).
kubectl version --client
kubectl get nodes

The node should show Ready. Only continue when it does.

Deploy

  1. Create folder k8s-practical, open it, and create deployment.yaml:
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:latest
        ports:
        - containerPort: 80
kubectl apply -f deployment.yaml
kubectl get deployments
kubectl get pods

Wait until all three pods say Running and READY is 1/1. Re-run kubectl get pods if some show ContainerCreating.

kubectl get pods -o wide
kubectl delete -f deployment.yaml

The last command cleans up. Run it only after your screenshots.

Screenshots: kubectl get nodes; kubectl get deployments showing 3/3; kubectl get pods with three Running pods.
RememberIndentation in the YAML must be exact, with spaces only. Run kubectl get nodes before every deploy: a Ready node means you are connected. The first run needs internet to pull the nginx image. If kubectl is not found, close and reopen VS Code after Kubernetes finishes starting.
Troubleshooting: error “failed to download openapi ... Authentication required ... Hudson”This is not a YAML problem. With no cluster configured, kubectl defaults to localhost:8080, where your Jenkins container from Practical 6 answers with its login page. It means Kubernetes is not enabled or not selected. Do not use --validate=false, because it only hides the problem.
  1. Run kubectl config get-contexts. If there is no docker-desktop entry, open Docker Desktop, go to Settings, then Kubernetes, tick Enable Kubernetes and click Apply & restart. Wait for the green Kubernetes status (3 to 10 minutes the first time).
  2. If docker-desktop is listed but has no * beside it, run kubectl config use-context docker-desktop.
  3. Close and reopen the VS Code terminal.
  4. Run kubectl config current-context (should say docker-desktop) and kubectl get nodes (should show Ready).
  5. Run kubectl apply -f deployment.yaml again.
Troubleshooting: pods stuck in ErrImagePullCheck your internet connection and run kubectl get pods again after a minute.
Alternative if Docker Desktop Kubernetes will not startInstall minikube, run minikube start, and use the same commands.

10.API testing with Postman

GET request to jsonplaceholder, verify status 200, show the body.

Theory: what we did and achieved

Concept: An API lets programs exchange data over HTTP. A GET request asks the server for data. The response has a status code, where 200 means success, and a body, here in JSON format. Postman is a tool for sending requests and writing tests against the responses.

What we did: We sent a GET request to the JSONPlaceholder posts/1 endpoint, added a test that the status is 200, and viewed the JSON body.

What we achieved: We tested an API without writing an application, and confirmed both the status code and the data. API testing like this catches backend problems early in the delivery pipeline.

  1. Install Postman from postman.com/downloads (or use Postman on the web). You can skip signing in if offered a “Lightweight API client”.
  2. Click New → HTTP (or the + tab). Keep the method as GET.
  3. Enter the URL:
https://jsonplaceholder.typicode.com/posts/1
  1. Click the Scripts tab, which sits after Body in the row under the URL bar (older versions call it Tests). Choose the Post-response sub-tab and add:
pm.test("Status code is 200", function () {
    pm.response.to.have.status(200);
});
  1. Click Send. The test runs only when you send the request, so send again if you added the script after your first send.
  2. Check the status at the top right of the response: 200 OK. The Test Results tab shows the test passed.
  3. The Body section displays the response, which looks like { "userId": 1, "id": 1, "title": "...", "body": "..." }.
Screenshots: the request with URL and GET; the response body; status 200 OK; Test Results showing PASS.
RememberThe status code and the test result are separate things. Screenshot both. Use the Pretty view for the body. This needs an internet connection.

11.Web testing with Selenium

Open Google, search for DevOps, print the page title.

Theory: what we did and achieved

Concept: Selenium is a tool for automating web browsers. A script can open pages, find elements such as a search box, type text, press keys and read results, just as a person would. This is used for automated functional testing of web applications.

What we did: We wrote a Python script that opens Chrome, loads Google, finds the search box, types DevOps, submits it and prints the page title.

What we achieved: We automated a manual browser task and read a result from the page. Tests like this can run inside a CI/CD pipeline to check that a website still works after every change.

  1. Install Python 3 from python.org. During install tick Add python.exe to PATH. Install Google Chrome if missing.
  2. Create a folder selenium-practical in VS Code. In the terminal:
python --version
pip install selenium
  1. Create google_search.py:
from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.common.keys import Keys
import time

driver = webdriver.Chrome()
driver.get("https://www.google.com")
time.sleep(2)

box = driver.find_element(By.NAME, "q")
box.send_keys("DevOps")
box.send_keys(Keys.RETURN)
time.sleep(3)

print("Page title:", driver.title)
driver.quit()
  1. Run it:
python google_search.py

Chrome opens, searches, and the terminal prints Page title: DevOps - Google Search.

Screenshots: the script in VS Code; the terminal output with the page title; the Chrome window showing the results.
RememberName the file anything except selenium.py, which breaks the import. Selenium 4.6 or newer downloads the Chrome driver itself, so you do not need to install one. Keep your internet on and do not close the Chrome window while it runs.
Troubleshooting: Google shows a cookie popup or CAPTCHA, or pip is not foundThe search box may not be found. Click through the popup manually while the script waits, or increase the first time.sleep(2) to time.sleep(10). If pip is not found, use python -m pip install selenium.

12.Create a Grafana dashboard

A dashboard with one panel showing CPU or memory from a metrics source.

Theory: what we did and achieved

Concept: Monitoring means collecting and viewing system metrics to understand health and performance. Node Exporter produces CPU and memory metrics, Prometheus collects and stores them, and Grafana connects to Prometheus as a data source and draws them as dashboards with panels.

What we did: We started Grafana, Prometheus and Node Exporter with Docker Compose, added Prometheus as a data source in Grafana, and built a dashboard panel with a CPU or memory query.

What we achieved: We built a live dashboard showing resource usage. This covers the monitoring stage of DevOps, where teams watch running systems and spot problems early.

Docker Desktop must be running. This setup runs Grafana, Prometheus (stores metrics) and Node Exporter (produces CPU and memory numbers) together with Compose.
  1. Create a folder grafana-practical and open it in VS Code.
  2. Create prometheus.yml:
global:
  scrape_interval: 5s
scrape_configs:
  - job_name: node
    static_configs:
      - targets: ['node-exporter:9100']
  1. Create docker-compose.yml:
services:
  prometheus:
    image: prom/prometheus
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
  node-exporter:
    image: prom/node-exporter
  grafana:
    image: grafana/grafana
    ports:
      - "3000:3000"
docker compose up -d
docker compose ps
  1. Check Prometheus works: open http://localhost:9090/targets. The node target should show UP. Wait a minute if not.
  2. Open http://localhost:3000. Log in with admin / admin and skip or set a new password.
  3. Add the data source: Connections → Data sources → Add data source → Prometheus. Set URL to http://prometheus:9090. Click Save & test and confirm the green success message.
  4. Create the dashboard: Dashboards → New → New dashboard → Add visualization. Pick the Prometheus data source.
  5. In the query box (switch to Code mode) enter a CPU query:
100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[1m])) * 100)

For memory use this instead:

node_memory_MemAvailable_bytes
  1. Click Run queries, set the panel title (for example CPU Usage), then click Save dashboard and give it a name.

Stop everything after the exam screenshots:

docker compose down
Screenshots: Prometheus targets showing UP; the data source “Save & test” success; the finished dashboard with the panel showing a graph.
RememberInside Grafana the data source address is http://prometheus:9090, not localhost, because the containers talk to each other by service name. Wait 1 to 2 minutes after starting so the graph has data points, and set the time range (top right) to Last 15 minutes.
Troubleshooting: “No data” in the panel, or port 3000 or 9090 in useNo data: check the targets page shows UP and the time range is recent.
Port in use: stop other containers with docker ps then docker rm -f NAME.
